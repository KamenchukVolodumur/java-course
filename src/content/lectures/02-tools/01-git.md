## Git

Git — це розподілена система контролю версій. Вона надає інструменти для керування **репозиторієм**. Репозиторій — це просто набір збережених станів **робочого каталогу**. Такий збережений стан називається **комітом** (commit).

Зазвичай репозиторій — це каталог `.git` усередині робочого каталогу. У ньому лежать файли, що описують коміти, разом зі збереженим вмістом робочого каталогу.

```bash
mkdir repo
cd repo
git init
ls -l .git
```

Ця команда створює порожній репозиторій у порожньому робочому каталозі: у ньому ще немає жодної збереженої версії.

```text
-rw-rw-r-- 1 user user   92 Mar 22 10:11 config        # локальна конфігурація репозиторію
-rw-rw-r-- 1 user user   73 Mar 22 10:11 description   # опис репозиторію для людей
-rw-rw-r-- 1 user user   23 Mar 22 10:11 HEAD          # вказівник на «поточний» коміт
drwxrwxr-x 4 user user 4096 Mar 22 10:11 objects       # збережені об'єкти: коміти, стани файлів і каталогів
drwxrwxr-x 4 user user 4096 Mar 22 10:11 refs          # посилання, тобто імена комітів
```

Робочий каталог разом із `.git` можна вільно переносити й копіювати: `.git` не містить абсолютних шляхів. Видалення каталогу `.git` знищує репозиторій з усією інформацією про версії, але, звісно, не чіпає самого робочого каталогу.

### Об'єкти

Репозиторій складається з об'єктів, які зберігаються в каталозі `.git/objects`. Git визначає 4 типи об'єктів (blob, tree, commit, annotated tag), з яких найважливіші перші три:

* **blob** — збережений вміст якогось файлу з робочого каталогу;
* **tree** — збережений вміст каталогу (словник «ім'я → об'єкт»);
* **commit** — збережений стан робочого каталогу з додатковою інформацією про версію.

Створений об'єкт **незмінний**: його вміст змінити неможливо. Завдяки цьому вміст можна використовувати для ідентифікації об'єкта! Git розпізнає об'єкти за **хешем SHA-1 їхнього вмісту**. Хеш залежить лише від вмісту: інший вміст — інший ідентифікатор — інший об'єкт.

Хеш файлу можна обчислити вручну командою `hash-object`. Для цього навіть не потрібен репозиторій:

```bash
echo Hi! > hi.txt
git hash-object hi.txt   # 663adb09143767984f7be83a91effa47e128c735
```

Обчислений хеш буде однаковим на кожному комп'ютері, бо вміст файлу той самий. Зміна вмісту змінить хеш.

Файл, доданий до репозиторію (наприклад, у складі коміту), потрапляє в каталог `objects` як об'єкт blob з ідентифікатором, що дорівнює його хешу.

```bash
cd repo
echo Hi! > hi.txt
git add hi.txt
git commit -m "Initial commit"
git cat-file blob 663ad
```

Каталог `.git/objects` поділено на підкаталоги за першими двома символами хешу. Як видно з прикладу, для ідентифікації об'єкта досить кількох перших символів SHA-1 — стільки, щоб уникнути неоднозначності.

Зберегти стан окремого файлу недостатньо для версіонування проєкту: потрібно зберігати стан цілих каталогів. Для цього існує об'єкт tree. Команда `git commit` створила кілька об'єктів:

```bash
find .git/objects -type f
git cat-file -t 8da9      # tree
git ls-tree 8da9
```

Один з них — tree. Його вміст — це перелік вмісту каталогу, стан якого він описує:

```text
100644 blob 663adb09143767984f7be83a91effa47e128c735    hi.txt
```

Наш об'єкт містить лише один запис, бо в момент `git commit` у робочому каталозі був один файл. Для кожного елемента каталогу tree зберігає:

* права доступу (`100644` = `rw-r--r--`);
* тип (blob або tree);
* ідентифікатор об'єкта (SHA-1);
* ім'я в каталозі (`hi.txt`).

Об'єкт tree може містити інші об'єкти tree. Так описуються довільно вкладені структури каталогів:

```text
Commit da14b73
└── Tree 8dab03            (корінь проєкту)
    ├── Blob fe493f7       pom.xml
    ├── Blob 28c7351       README.md
    └── Tree 9c75956       src/
        ├── Blob ab2ea75   Main.java
        └── Blob db09143   Util.java
```

Якщо в каталозі кілька файлів з однаковим вмістом, tree кілька разів посилатиметься на той самий об'єкт:

```bash
cp hi.txt hey.txt
git add hey.txt
git commit -m "Copied hi.txt"
git ls-tree a5250
```

```text
100644 blob 663adb09143767984f7be83a91effa47e128c735    hey.txt
100644 blob 663adb09143767984f7be83a91effa47e128c735    hi.txt
```

Ідентифікатор tree — це SHA-1 цього переліку, який містить хеші вкладених елементів. Зміна вмісту `hi.txt` змінює його хеш, отже змінюється вміст кореневого tree, а з ним і його хеш.

**Коміти** — головні об'єкти репозиторію, які створюються під час збереження версії проєкту:

```bash
git cat-file commit a7f3
```

```text
tree a5250f7c6ad5260e28003ba5a0b1841b752918e3
parent 23d9585ca2a2fe493f79c75956ab4d815da14b73
author Jan Kowalski <jan@example.com> 1742665566 +0100
committer Jan Kowalski <jan@example.com> 1742665566 +0100

Copied hi.txt
```

З нього можна прочитати:

* ідентифікатор збереженого стану робочого каталогу (`tree`);
* ідентифікатори попередніх комітів (`parent`);
* автора (`author`) і час створення змін;
* того, хто застосував коміт (`committer`), і час застосування;
* повідомлення, що описує версію (`Copied hi.txt`).

> [!IMPORTANT]
> Коміт містить **стан усього проєкту**, а не внесені зміни! Різницю (diff) Git обчислює щоразу, порівнюючи два знімки.

SHA-1 коміту обчислюється з наведених полів. Зміна будь-якого з них, навіть лише повідомлення, вимагає створити новий коміт з іншим SHA-1. Тому «змінити» коміт (`git commit --amend`, `rebase`) насправді означає створити новий і перевести на нього гілку.

### Гілки

Користуватися хешами SHA-1 людині незручно. Замість «подивись на версію `23d9585ca2a2fe493f79c75956ab4d815da14b73`» простіше мати зрозуміле ім'я ревізії. Такі посилання називаються **гілками** (branches).

```bash
git branch -v
# * master a7f3d48 Copied hi.txt
```

Технічно гілки — це файли в каталозі `.git/refs/heads/`, які зберігають SHA-1 коміту, що його називають (Git може також упакувати їх в один файл `.git/packed-refs`):

```bash
cat .git/refs/heads/master
# a7f3d48e135b4f4deb9a985ed7058b70491d7c71
```

Перелік гілок — це фактично перелік цього каталогу. Створення гілки, що вказує на коміт, — це створення такого самого файлу:

```bash
git branch feature a7f3d48
git branch -v
#   feature a7f3d48 Copied hi.txt
# * master  a7f3d48 Copied hi.txt
ls .git/refs/heads
# feature master
```

Звідси важливий факт:

> [!IMPORTANT]
> Гілка — це лише **ім'я коміту**!

Гілки змінювані: коли створюється новий коміт, активна гілка **переміщується** на нього. Git підтримує й незмінні імена комітів — **теги** (`git tag v1.0`).

### HEAD

А що таке *активна гілка*? У репозиторії є спеціальне посилання `HEAD` (файл `.git/HEAD`), яке вказує на поточний коміт, з яким ми працюємо. `HEAD` може вказувати на коміт опосередковано, через гілку, або безпосередньо. Типова ситуація — опосередкована:

```bash
cat .git/HEAD
# ref: refs/heads/master
```

Саме про таку ситуацію кажуть, що ми *перебуваємо на гілці*. `HEAD` вказує на `master`, а `master` — на конкретний коміт. Обидва імені позначають той самий коміт:

```text
HEAD ──► master ──► Commit a7f3 ──parent──► Commit 23d9 ──parent──► (немає)
                        │                       │
                      tree                    tree
                        ▼                       ▼
                    Tree a525               Tree 8da9
                     │    │                     │
                     ▼    ▼                     ▼
                     Blob 663a (hi.txt, hey.txt — той самий вміст)
```

Для переміщення `HEAD` служить `git checkout` (або сучасніші `git switch` для гілок і `git restore` для файлів). Зміна `HEAD` змінює вміст робочого каталогу на стан, збережений у цільовому коміті:

```bash
git checkout 23d9
cat .git/HEAD
# 23d9585ca2a2fe493f79c75956ab4d815da14b73
```

Тепер `HEAD` вказує на коміт безпосередньо. Це стан **detached HEAD**: він нормальний, коли переглядаємо старі ревізії.

```text
master ──► Commit a7f3 ──parent──► Commit 23d9 ◄── HEAD
```

Коміт, на який вказує `HEAD`, автоматично стає батьком нових ревізій:

```bash
git checkout master          # HEAD -> master -> a7f3
touch empty.txt
git add empty.txt
git commit -m "Add empty file"
# [master eef04fe] Add empty file
#  1 file changed, 0 insertions(+), 0 deletions(-)
git cat-file commit eef0
# tree 580e44691fcd53fb04aebbd71fe23b5c626afec8
# parent a7f3d48e135b4f4deb9a985ed7058b70491d7c71
# ...
```

Під час цієї операції активна гілка переміщується на новий коміт. У стані detached HEAD активної гілки немає, тож створювати там нові коміти неприродно: щойно ви перейдете на іншу гілку, до них не вестиме жодне ім'я.

### Індекс

Перед створенням коміту зазвичай виконують `git add`. Навіщо? У процесі створення коміту беруть участь три незалежні стани робочого каталогу:

* сам **робочий каталог** з поточним станом файлів;
* **`HEAD`** — відносно нього готуються зміни (він стане батьком);
* **індекс** (staging area) — проміжний стан, у який вибірково додають зміни перед комітом.

Це дозволяє вибірково формувати вміст наступного коміту. Наприклад, у деяких файлах можуть бути особисті «брудні» зміни, які не мають потрапити в нову ревізію, але й викидати їх не хочеться.

Технічно індекс зберігається у файлі `.git/index`. Його можна показати командою `ls-files`:

```bash
git ls-files --stage
# 100644 e69de29bb2d1d6434b8b29ae775ad8c2e48c5391 0       empty.txt
# 100644 663adb09143767984f7be83a91effa47e128c735 0       hey.txt
# 100644 663adb09143767984f7be83a91effa47e128c735 0       hi.txt
```

Це дуже схоже на об'єкт tree, бо майже ним і є! Під час `git commit` саме стан індексу зберігається як новий об'єкт tree, навколо якого створюється об'єкт commit.

`git checkout` відновлює не лише робочий каталог до стану з коміту, а й синхронізує з ним індекс. У *чистому* стані репозиторію `HEAD == index == workdir`:

```bash
git status
# On branch master
# nothing to commit, working tree clean
```

Змінивши файли в робочому каталозі, отримуємо `HEAD == index != workdir`:

```bash
echo "not really" > empty.txt
git status
# Changes not staged for commit:
#         modified:       empty.txt
git diff
# diff --git a/empty.txt b/empty.txt
# @@ -0,0 +1 @@
# +not really
```

`git diff` порівнює робочий каталог з індексом. Додавши зміну до індексу, отримуємо `HEAD != index == workdir`:

```bash
git add empty.txt
git status
# Changes to be committed:
#         modified:       empty.txt
git diff              # порожньо: робочий каталог == індекс
git diff --staged     # індекс vs HEAD (синонім --cached)
# +not really
```

Під час додавання файлу до індексу створюється новий об'єкт blob з його вмістом. Об'єкти tree створює лише `git commit`.

Тепер можна знову змінити робочий каталог і отримати `HEAD != index != workdir`:

```bash
echo "hey!" > empty.txt
git status
# Changes to be committed:
#         modified:       empty.txt
# Changes not staged for commit:
#         modified:       empty.txt
git diff
# -not really
# +hey!
```

Якщо тепер виконати `git commit`:

* індекс буде збережено як новий об'єкт tree;
* буде створено новий об'єкт commit, який вказує на цей tree, а в поле `parent` потрапить поточний `HEAD`;
* гілку, на яку вказує `HEAD`, буде переміщено на новий коміт.

Отримаємо `HEAD == index != workdir`: остання зміна лишиться в робочому каталозі, бо `git commit` його не чіпає.

```bash
git commit -m "Filled empty file"
# [master 401c27f] Filled empty file
git status
# Changes not staged for commit:
#         modified:       empty.txt
```

> [!TIP]
> `git add -p` дозволяє додавати до індексу не цілі файли, а окремі фрагменти змін: зручно, коли в одному файлі змішалися дві незалежні правки.

### Reset

Одна з базових операцій, `git reset`, часто викликає труднощі через свою багатофункціональність. Попри «руйнівну» назву, `reset` насправді **переміщує гілку** на вказаний коміт. Додатково він може водночас змінити стан індексу й робочого каталогу на стан цієї ревізії.

`git reset` має 3 режими.

`git reset --soft` переміщує посилання, збережене в `HEAD`, на вказаний коміт. Стан робочого каталогу та індексу не змінюється:

```bash
git reset --soft HEAD^       # HEAD^ — перший батько HEAD
git status
# Changes to be committed:
#         modified:       empty.txt
# Changes not staged for commit:
#         modified:       empty.txt
```

Ми повернулися до стану `HEAD != index != workdir`, тобто ніби скасували `git commit`. Сам коміт, хоч і без імені, досі існує, і до нього можна повернутися:

```bash
git reset --soft 401c
```

`git reset --mixed` (режим за замовчуванням) робить те саме, що `--soft`, і додатково відновлює індекс до стану вказаного коміту:

```bash
git reset --mixed HEAD^
git diff
# +hey!
```

Тепер `HEAD == index != workdir`, а робочий каталог не змінився.

`git reset --hard` змінює все: гілку `HEAD`, індекс і робочий каталог переводить у стан вказаної ревізії. **Незакомічені зміни в робочому каталозі втрачаються безповоротно!**

```bash
git reset --hard 401c
git status
# nothing to commit, working tree clean
```

> [!TIP]
> «Загублені» коміти (на які більше не вказує жодна гілка) можна знайти через `git reflog`: Git кілька тижнів пам'ятає всі попередні положення `HEAD`.

### Merge

Репозиторій — це набір комітів, кожен з яких містить список посилань на своїх батьків (від 0 до n). Отже, будь-який репозиторій — це **орієнтований ациклічний граф**: вершини — коміти, ребра — вказівники на батьків. Граф можна побачити командою `git log`:

```bash
git log --oneline --graph --all
# * 401c27f (HEAD -> master) Filled empty file
# * eef04fe Add empty file
# * a7f3d48 (feature) Copied hi.txt
# * 23d9585 Initial commit
```

Поки що граф — це список: проєкт розвивався лінійно. Але один коміт може бути батьком кількох ревізій. Зазвичай так буває, коли кілька авторів одночасно починають роботу з тієї самої ревізії:

```bash
git checkout feature
echo "Feature Hi!" > hi.txt
git add hi.txt
git commit -m "Featurized hi.txt"
git log --oneline --graph --all
# * 5e11eea (HEAD -> feature) Featurized hi.txt
# | * 401c27f (master) Filled empty file
# | * eef04fe Add empty file
# |/
# * a7f3d48 Copied hi.txt
# * 23d9585 Initial commit
```

На коміті `a7f3d48` історія розгалузилася. Рано чи пізно незалежно розроблені гілки треба об'єднати в одну узгоджену ревізію. Для цього є `git merge`, який створює коміти з кількома батьками:

```bash
git merge --no-edit master
git log --oneline --graph --all
# *   1296142 (HEAD -> feature) Merge branch 'master' into feature
# |\
# | * 401c27f (master) Filled empty file
# | * eef04fe Add empty file
# * | 5e11eea Featurized hi.txt
# |/
# * a7f3d48 Copied hi.txt
# * 23d9585 Initial commit
git cat-file -p HEAD
# tree 8c1f710ff54a3848913a130fbd58b1247827b1ed
# parent 5e11eea4a4f3199d1a097e0716c4afa1c0724317
# parent 401c27fd94595bc9565d76e389fa5923febf2302
# ...
```

Новий merge-коміт поєднує стани робочого каталогу з обох батьків. Один батько — це завжди `HEAD`, другий — те, що передали в аргументі. Злиття відбулося автоматично, бо зміни не конфліктували.

Для злиття Git використовує алгоритм **трибічного злиття** (three-way merge). Він враховує три стани: два з комітів, що зливаються (`5e11eea` і `401c27f`), і їхнього найближчого спільного предка — точку розгалуження `a7f3d48`.

```text
              5e11eea 'Feature Hi!'  ◄── feature
             /                    \
a7f3d48 'Hi!'                      1296142 'Feature Hi!'  (новий merge-коміт)
             \                    /
              401c27f 'Hi!'      ◄── master
```

У прикладі вище вміст `hi.txt` в одній із версій такий самий, як у спільного предка. Тож злиття тривіальне: обирається та версія, яка відрізняється. Алгоритм припускає, що коли стан в одній гілці не змінився, а в іншій змінився, то бажаний результат — зміна.

Якщо всі три версії однакові, усе очевидно. А якщо всі три різні? Тоді виникає **конфлікт** змін:

```bash
git reset --hard HEAD^
git checkout master
echo "Master Hi!" > hi.txt
git add hi.txt && git commit -m "Masterized hi.txt"
git merge feature
# Auto-merging hi.txt
# CONFLICT (content): Merge conflict in hi.txt
# Automatic merge failed; fix conflicts and then commit the result.
```

Операцію `git merge` виконано частково й зупинено перед створенням merge-коміту. Робочий каталог та індекс містять частково злитий стан. Файли, які алгоритм не зміг обробити автоматично, містять маркери в місцях конфліктів:

```bash
cat hi.txt
# <<<<<<< HEAD
# Master Hi!
# =======
# Feature Hi!
# >>>>>>> feature
```

Тепер користувач мусить вручну розв'язати конфлікт, замінивши позначені фрагменти правильним вмістом, і завершити злиття:

```bash
echo "Feature master Hi!" > hi.txt
git add hi.txt
git commit
```

Злиття — лише один з інструментів поєднання змін у Git. Варто також знати `rebase` (перенесення комітів на нову основу, лінійна історія), `rebase -i` (редагування, об'єднання та перевпорядкування комітів) і `cherry-pick` (застосування окремого коміту в іншій гілці).

### Віддалені репозиторії

Git — **розподілена** система контролю версій, призначена для роботи над одним проєктом з багатьох комп'ютерів. Зазвичай кожен автор має власний репозиторій на своїй машині й синхронізує його з віддаленими репозиторіями через мережевий протокол (HTTPS або SSH). Ідентифікатори об'єктів, обчислені з їхнього вмісту, — глобальні: вони однакові в усіх репозиторіях.

Адреси віддалених репозиторіїв зберігаються в `.git/config` і налаштовуються командою `git remote`. Для навчання «віддаленим» може бути інший каталог на тому самому комп'ютері. Приклади нижче продовжують стан репозиторію з кінця розділу про reset (до злиттів).

```bash
mkdir origin && cd origin
# інша початкова гілка: Git не дозволяє push у гілку, яка зараз активна в не-bare репозиторії
git init --initial-branch=main
cd ../repo
git remote add origin ../origin
```

Під час клонування Git автоматично додає віддалений репозиторій з ім'ям `origin`, що вказує на джерело.

Основні команди, які спілкуються з віддаленим репозиторієм:

* `git clone`
* `git fetch`
* `git pull`
* `git push`

Решта розглянутих команд віддалену копію ніяк не чіпають.

`git push` оновлює віддалені посилання: гілка у віддаленому репозиторії, що відповідає локальній, починає вказувати на той самий коміт. Попутно надсилаються об'єкти (commit, tree, blob), яких у віддаленому репозиторії бракує.

```bash
git push --set-upstream origin master
# Enumerating objects: 11, done.
# Writing objects: 100% (11/11), 976 bytes | 976.00 KiB/s, done.
# To ../origin
#  * [new branch]      master -> master
# branch 'master' set up to track 'origin/master'.
```

За замовчуванням Git не знає, яка віддалена гілка відповідає локальній `master`. Цей зв'язок налаштовується один раз через `--set-upstream` (`-u`).

Віддалений репозиторій був порожній. `git push` створив у ньому гілку `master` і встановив її на коміт `401c`. Для цього довелося надіслати цей коміт і всі його залежності, проходячи вказівниками `parent` до самого *початку* історії.

```bash
git branch -va
#   feature               a7f3d48 Copied hi.txt
# * master                401c27f Filled empty file
#   remotes/origin/master 401c27f Filled empty file
```

Операції з віддаленими репозиторіями змінюють не лише посилання там, а й їхні локальні відповідники. `git push` створив локальне посилання `origin/master`, що вказує туди ж, куди `master` у репозиторії `origin`. Такі посилання — не гілки: їх не можна перемістити інакше, ніж через обмін з віддаленим репозиторієм.

Тим часом у віддаленому репозиторії можуть з'явитися нові коміти й гілки:

```bash
cd ../origin
git checkout -b development master
echo 'public class Main { public static void main(String[] a) { } }' > Main.java
git add Main.java && git commit -m "Added Main.java"
```

`git fetch` оновлює всі локальні відповідники віддалених гілок і завантажує потрібні об'єкти:

```bash
cd ../repo
git fetch
# From ../origin
#  * [new branch]      development -> origin/development
git branch -va
#   feature                    a7f3d48 Copied hi.txt
# * master                     401c27f Filled empty file
#   remotes/origin/development e0e64f5 Added Main.java
#   remotes/origin/master      401c27f Filled empty file
```

У локальному репозиторії з'явилося посилання `origin/development` на новий коміт. Можна створити від нього локальну гілку й продовжити роботу:

```bash
git switch development       # створить локальну гілку, що відстежує origin/development
```

`git pull` поєднує дві операції: `git fetch` + `git merge <віддалене посилання>`. Тобто робить те саме, що fetch, а потім зливає локальну гілку з її віддаленим відповідником і, можливо, створює merge-коміт (з `--rebase` замість злиття виконується rebase).

### .gitignore

Не все з робочого каталогу має потрапляти в репозиторій. Результати збирання, налаштування IDE і секрети перелічують у файлі `.gitignore`:

```text
# результати збирання Maven / Gradle
target/
build/
*.class
*.jar

# IDE
.idea/
*.iml
.vscode/

# секрети й локальні налаштування
.env
```

Шаблони діють на файли, які ще **не відстежуються**. Файл, який уже закомічено, треба спершу прибрати з індексу: `git rm --cached file`.
