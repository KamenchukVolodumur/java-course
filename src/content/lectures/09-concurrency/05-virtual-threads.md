## Навіщо віртуальні потоки

Найпростіший спосіб писати серверний код — **потік на запит**: кожен запит обробляється в окремому потоці звичайним послідовним кодом, що блокується на мережі й базі даних. Проблема в кількості: платформний потік — це потік ОС з великим стеком, і тисячі таких потоків вичерпують пам'ять задовго до того, як вичерпається процесор. Більшість часу ці потоки нічого не роблять, лише **чекають** на введення-виведення.

Асинхронні ланцюжки (`CompletableFuture`) розв'язують проблему, але ціною: код розбивається на продовження, втрачається звичайний стек викликів, `try/catch` і цикли доводиться виражати комбінаторами.

**Віртуальні потоки** (Java 21) дають обидві переваги: код пишуть у блокувальному стилі, а потік ОС під час очікування не займається.

* Віртуальний потік — це об'єкт `Thread`, яким керує **JVM**, а не ОС. Його стек зберігається в купі й росте за потреби, тож створення коштує кількасот байтів.
* Виконується віртуальний потік на одному з небагатьох платформних **потоків-носіїв** (carrier threads) — пулі `ForkJoinPool` з кількістю потоків, що дорівнює кількості ядер.
* Коли віртуальний потік доходить до **блокувальної** операції (`sleep`, читання з сокета, `BlockingQueue.take`, `lock()`), JVM **демонтує** його з носія: зберігає його стек у купі й звільняє носій для іншого віртуального потоку. Коли операція завершується, потік знову **монтується** на вільний носій і продовжує роботу з того самого місця.

```text
        віртуальні потоки (мільйони)       VT1   VT2   VT3   VT4   ...
                                             │           │
                                  змонтовані ▼           ▼     решта чекають у купі
        потоки-носії (= ядра)             [ carrier-1 ] [ carrier-2 ]
                                             │           │
        потоки ОС                         [ OS thread ] [ OS thread ]
```

> [!NOTE]
> Збереження стека й відновлення виконання з того самого місця — та сама ідея **продовження** (continuation), що й в асинхронних ланцюжках. Різниця в тому, що тут продовження створює JVM автоматично, а не програміст вручну.

## Створення

```java
Thread vt = Thread.ofVirtual().name("virtual-", 0).start(() -> System.out.println("привіт"));
vt.join();

Thread.startVirtualThread(() -> System.out.println("коротший запис"));

System.out.println(vt.isVirtual());            // true

try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> f = executor.submit(() -> download(url));   // новий віртуальний потік на задачу
    System.out.println(f.get());
}
```

Віртуальні потоки завжди daemon (не утримують JVM) і мають однаковий пріоритет. Решта API — `join`, `interrupt`, `ThreadLocal`, `synchronized` — працює як зі звичайними потоками.

## Масштаб

Десять тисяч задач, кожна з яких секунду «чекає на мережу»:

```java
Instant start = Instant.now();
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i -> executor.submit(() -> {
        Thread.sleep(Duration.ofSeconds(1));
        return i;
    }));
}
System.out.println("Час: " + Duration.between(start, Instant.now()).toMillis() + " мс");   // ~1000 мс
```

Програма завершиться приблизно за секунду. З `Executors.newFixedThreadPool(200)` вона працювала б 50 секунд (10 000 / 200), а створення 10 000 платформних потоків помітно навантажило б систему.

## Коли віртуальні потоки допомагають

* **Допомагають**, коли задач багато й вони здебільшого **чекають**: HTTP-сервери, клієнти REST і баз даних, обробка черг повідомлень. Пропускна здатність зростає, бо паралельно очікувати можуть мільйони задач.
* **Не допомагають** для обчислень (CPU-bound): ядер не стане більше, а віртуальний потік, що рахує, займає носій так само, як платформний. Для обчислень — паралельні потоки Stream API і `ForkJoinPool` (наступна сторінка).
* Віртуальні потоки не роблять код швидшим: окрема операція виконується так само довго. Зростає лише кількість одночасних операцій.

## Правила використання

### Не об'єднуйте віртуальні потоки в пули

Пул існує, щоб повторно використовувати **дорогі** ресурси. Віртуальний потік дешевий, тож його створюють на кожну задачу й викидають. Пул віртуальних потоків лише обмежує кількість одночасних задач, а для цього є кращий інструмент.

### Обмежуйте конкурентність семафором

Якщо зовнішній ресурс витримує обмежену кількість одночасних запитів (наприклад, 10 з'єднань з базою), кількість віртуальних потоків обмежують не пулом, а **семафором**:

```java
private final Semaphore dbPermits = new Semaphore(10);

String query(String sql) throws InterruptedException {
    dbPermits.acquire();                  // віртуальний потік чекає, не займаючи носія
    try {
        return database.execute(sql);
    } finally {
        dbPermits.release();
    }
}
```

### Закріплення (pinning)

Віртуальний потік не може бути демонтований, якщо він **закріплений** (pinned) на носії. Тоді блокувальна операція блокує й сам носій, і якщо таких потоків стільки ж, скільки носіїв, решта віртуальних потоків перестають виконуватися. Закріплення виникає, коли потік виконує нативний код (через JNI чи FFM). До Java 24 закріплення спричиняло також блокування всередині `synchronized`, тому в коді для старіших версій рекомендували `ReentrantLock`. Від Java 24 `synchronized` віртуальні потоки не закріплює.

Діагностика: `-Djdk.tracePinnedThreads=full` (до Java 24) або подія JFR `jdk.VirtualThreadPinned`.

### ThreadLocal і ScopedValue

`ThreadLocal` працює й у віртуальних потоках, але з мільйонами потоків мільйони копій кешованих об'єктів займають багато пам'яті. Для передачі контексту вниз стеком викликів (поточний користувач, ідентифікатор запиту) призначено **`ScopedValue`** (Java 25): незмінне значення, видиме лише в межах заданого виклику.

```java
private static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

void handle(Request request) {
    ScopedValue.where(REQUEST_ID, request.id()).run(() -> processRequest(request));
}

void log(String message) {
    System.out.println("[" + REQUEST_ID.get() + "] " + message);   // доступне без передачі параметром
}
```

## Структурована конкурентність

Коли задача запускає кілька підзадач паралельно, звичайні `Future` не пов'язані між собою: якщо одна підзадача впала, інші продовжують працювати, а якщо батьківську задачу перервали, підзадачі про це не дізнаються. **Структурована конкурентність** (`StructuredTaskScope`, preview-API у Java 21–25, деталі API змінювалися між версіями) прив'язує час життя підзадач до блоку коду, так само як блок `try` прив'язує час життя ресурсу:

```java
Response handle(int userId) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {                 // Java 25 (preview)
        Subtask<User> user = scope.fork(() -> findUser(userId));   // кожна підзадача — у віртуальному потоці
        Subtask<List<Order>> orders = scope.fork(() -> fetchOrders(userId));

        scope.join();                     // чекає на обидві; якщо одна впала — інша скасовується, join кидає виняток
        return new Response(user.get(), orders.get());
    }                                     // після блоку жодна підзадача гарантовано не працює
}
```

Переваги:

* помилка однієї підзадачі автоматично скасовує решту;
* переривання батьківського потоку скасовує всі підзадачі;
* дамп потоків показує ієрархію «задача → підзадачі».

> [!NOTE]
> Preview-API вимагає прапорця `--enable-preview` під час компіляції й запуску. Для коду без preview той самий шаблон реалізують через `ExecutorService` з `invokeAll` і ручне скасування `Future`.
