## Ідентичність і значення

Кожен об'єкт у Java має **ідентичність** (identity): два об'єкти з однаковим вмістом усе одно різні, і `==` це розрізняє. Для одних типів ідентичність природна: `Customer`, `Order`, `Window` — це конкретні сутності, які мають історію, і їх не можна випадково «скопіювати». Для інших вона зайва: дві точки `(1, 2)`, дві суми «10.00 зł» чи дві дати `2025-03-14` — це просто **однакові значення**.

Власних типів-значень (як `struct`) у Java поки немає: усе, що оголошує програміст, — посилальні типи. Семантику значень моделюють так:

* об'єкт **незмінний**: його стан не можна змінити після створення, тож спільне посилання поводиться як копія;
* **рівність за вмістом**: перевизначені `equals` і `hashCode`;
* операції повертають **нові** об'єкти замість зміни наявних.

```java
public record Point(double x, double y) {
    public Point translate(double dx, double dy) {
        return new Point(x + dx, y + dy);      // новий об'єкт, оригінал не змінюється
    }
}

Point p1 = new Point(3, -5);
Point p2 = p1;                  // копіюється посилання...
p2 = p2.translate(-2, 4);       // ...але змінити спільний об'єкт неможливо
System.out.println(p1);         // Point[x=3.0, y=-5.0]
System.out.println(p2);         // Point[x=1.0, y=-1.0]
System.out.println(new Point(1, -1).equals(p2));   // true: рівність за значенням
```

Для незмінного об'єкта різниця між «скопіювати значення» і «скопіювати посилання» зникає: жоден власник посилання не може змінити дані за спиною іншого.

## Records

**Record** (Java 16) — найкоротший спосіб оголосити незмінний тип-значення. Компілятор генерує `private final` поля, канонічний конструктор, аксесори, `equals`, `hashCode` і `toString` за всіма компонентами. Records неявно `final` і не можуть наслідувати інші класи (але можуть реалізовувати інтерфейси).

```java
public record Money(BigDecimal amount, String currency) {
    public Money {                                         // компактний конструктор: інваріанти
        Objects.requireNonNull(currency);
        amount = amount.setScale(2, RoundingMode.HALF_UP); // нормалізація перед присвоєнням полів
    }

    public Money plus(Money other) {
        if (!currency.equals(other.currency)) throw new IllegalArgumentException("Різні валюти");
        return new Money(amount.add(other.amount), currency);
    }
}
```

Records детально розглянуто на сторінці «Records» розділу «Можливості мови».

## Value-based класи стандартної бібліотеки

Багато класів JDK задокументовано як **value-based**: обгортки (`Integer`, `Double` …), `Optional`, усі класи `java.time` (`LocalDate`, `Instant`, `Duration`), `List.of(...)` тощо. Для них діє правило: **не покладайтеся на ідентичність**.

* не порівнюйте їх через `==` (лише `equals`);
* не синхронізуйтеся на них (`synchronized (anInteger)`);
* не використовуйте `System.identityHashCode` і `IdentityHashMap` з ними.

```java
LocalDate a = LocalDate.of(2025, 3, 14);
LocalDate b = LocalDate.parse("2025-03-14");
System.out.println(a.equals(b));   // true
System.out.println(a == b);        // false (або true — не визначено, не покладайтеся)

Integer x = 1000, y = 1000;
System.out.println(x == y);        // false: два різні об'єкти
```

> [!NOTE]
> Проєкт **Valhalla** (JEP 401, у стадії preview) додає до Java **value classes**: класи без ідентичності, які JVM може зберігати «пласко», без окремого об'єкта в купі. Value-based класи JDK у майбутньому стануть такими класами, тому правила вище вже сьогодні варто дотримуватися.

## Розміщення в пам'яті

Різниця між примітивами й об'єктами помітна в продуктивності, коли даних багато.

```java
double[] xs = new double[1_000_000];          // один суцільний блок: 8 МБ
Point[] points = new Point[1_000_000];        // масив посилань + мільйон окремих об'єктів
```

```text
double[]                          Point[]
┌─────┬─────┬─────┬───           ┌───┬───┬───┬───
│ 1.0 │ 2.5 │ 0.3 │ ...          │ ● │ ● │ ● │ ...
└─────┴─────┴─────┴───           └─┼─┴─┼─┴─┼─┴───
                                   ▼   ▼   ▼
                                 [заголовок|x|y] [заголовок|x|y] ...  (розкидані по купі)
```

Кожен об'єкт має **заголовок** (12–16 байтів на 64-бітній JVM) і вирівнювання до 8 байтів, тож `Point` з двома `double` займає ~32 байти замість 16, плюс 4–8 байтів на посилання в масиві. Обхід масиву об'єктів — це ще й стрибки по пам'яті, які гірше використовують кеш процесора.

Якщо продуктивність критична (обчислення, симуляції, ігри), застосовують підхід **«структура масивів»** (structure of arrays) замість «масиву структур»:

```java
final class Particles {                        // замість Particle[]
    final double[] x, y, vx, vy;

    Particles(int n) {
        x = new double[n]; y = new double[n];
        vx = new double[n]; vy = new double[n];
    }

    void step(double dt) {
        for (int i = 0; i < x.length; i++) {   // послідовний доступ, дружній до кешу і SIMD
            x[i] += vx[i] * dt;
            y[i] += vy[i] * dt;
        }
    }
}
```

> [!TIP]
> Не оптимізуйте передчасно. JIT уміє уникати виділення пам'яті для короткоживучих об'єктів, які не виходять за межі методу (**escape analysis**), а сучасні збирачі сміття дуже швидко обслуговують молоді об'єкти. Спершу пишіть зрозумілий код з records, а до примітивних масивів переходьте, коли профілювання покаже вузьке місце.

## Що обрати

| Ситуація | Вибір |
| --- | --- |
| Сутність з ідентичністю й життєвим циклом (`Customer`, `Order`, `Connection`) | звичайний клас, рівність за ідентичністю або за id |
| Невелике незмінне значення (`Point`, `Money`, `DateRange`, DTO) | `record` |
| Потрібна ієрархія з наслідуванням реалізації | клас (records не наслідуються) |
| Мільйони чисел у «гарячому» коді | примітиви й масиви примітивів |
| Одне значення з бібліотеки (`LocalDate`, `Duration`, `BigDecimal`) | value-based клас, порівняння через `equals`/`compareTo` |
