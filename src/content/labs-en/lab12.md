## Before You Start

> [!NOTE]
> **Lectures:** 14.4 "HTTP, REST and JSON", 14.5 "Databases and JDBC", 14.6 "Logging and Mockito", 14.7 "Docker" · **Time:** 3 h · **Points:** 10

The lab 10 code works, but an experienced engineer would find several problems in it during a review, problems that will show up in production:

* the database settings are hard-coded;
* the tests use H2, while production uses PostgreSQL: the SQL dialects differ, and tests on H2 will not notice it;
* the logs make it impossible to collect all the lines that belong to one request;
* running it requires installing a database by hand.

## Stage 1: Configuration and a Connection Pool (2 pts)

```java
public record AppConfig(String dbUrl, String dbUser, String dbPassword, int httpPort, int poolSize) {
    public static AppConfig fromEnv(Map<String, String> env);   // in main: AppConfig.fromEnv(System.getenv())
}
```

| Variable | Required | Default |
| --- | --- | --- |
| `DB_URL` | yes | — |
| `DB_USER` | yes | — |
| `DB_PASSWORD` | yes | — |
| `HTTP_PORT` | no | 8080 |
| `DB_POOL_SIZE` | no | 10 |

* A missing required variable or an invalid number → an `IllegalStateException` listing **all** the problems at once (`"Missing variables: DB_URL, DB_PASSWORD"`), not only the first one.
* `fromEnv` takes a `Map` instead of reading `System.getenv()` itself: that makes it easy to test.
* The record's `toString()` must **not** show the password (override it, `dbPassword=***`).
* The `DataSource` is a `HikariDataSource` with `poolSize`.
* There is one schema for H2 and PostgreSQL. Instead of `AUTO_INCREMENT`/`BIGSERIAL` use standard SQL: `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`.

> [!TIP]
> This is the **12-factor app** principle: the same artifact (a JAR, an image) runs in dev, test and prod, and only the environment variables differ.

## Stage 2: A REST API (2 pts)

Use `com.sun.net.httpserver.HttpServer` (see the "HTTP, REST and JSON" page) with `Executors.newVirtualThreadPerTaskExecutor()`.

| Method and path | Request body | Success | Errors |
| --- | --- | --- | --- |
| `GET /health` | — | 200 `{"status":"UP","db":"UP"}` | 503 if the database is unavailable (`SELECT 1`) |
| `GET /clients/{pesel}` | — | 200 the client | 404 |
| `POST /clients` | `{"pesel":"...","fullName":"..."}` | 201 + `Location: /clients/{pesel}` | 400 (validation), 409 (duplicate) |
| `POST /clients/{pesel}/deposits` | `{"amount":"50.00"}` | 200 the client | 400, 404 |
| `POST /transfers` | `{"from":"...","to":"...","amount":"30.00"}` | 204 | 400, 404, 422 (insufficient funds) |

* Mapping exceptions to statuses happens in **one** place (for example, an `ErrorMapper`), not in each handler:

| Exception | Status |
| --- | --- |
| `IllegalArgumentException`, malformed JSON | 400 |
| `NoSuchClientException` | 404 |
| `DuplicateClientException` | 409 |
| `InsufficientFundsException` | 422 |
| everything else | 500 (the body has **no** stack trace) |

* The error body is Problem Details (RFC 9457): `{"status":404,"title":"Not Found","detail":"Client not found","requestId":"..."}`, `Content-Type: application/problem+json`.
* Pass amounts in JSON **as strings** (`"50.00"`) and read them as `BigDecimal`.

```bash
curl -i -X POST localhost:8080/clients -d '{"pesel":"44051401359","fullName":"Jan Kowalski"}'
curl -i localhost:8080/clients/44051401359
curl -i -X POST localhost:8080/transfers -d '{"from":"44051401359","to":"02070803628","amount":"1000.00"}'
```

## Stage 3: An End-to-End requestId and an Access Log (2 pts)

One request passes through the handler, the service and the repository. To find **all** its lines in the logs, each line must contain the request id.

1. A wrapper (a filter) around every handler:
   * takes `X-Request-Id` from the request header if it is present and has a sane format (up to 64 characters of `[A-Za-z0-9-]`), otherwise generates a `UUID`;
   * puts it into `MDC.put("requestId", id)` and returns it in the `X-Request-Id` response header;
   * after handling, writes **one** access log line: `INFO  POST /transfers -> 422 (12 ms)`;
   * calls `MDC.clear()` in `finally`.
2. The Logback pattern: `%d{HH:mm:ss.SSS} %-5level [%X{requestId}] %logger{20} - %msg%n`.

```text
10:15:30.120 INFO  [7f3a9c1e-...] ClientService - Transfer *******1359 -> *******3628: 30.00
10:15:30.131 INFO  [7f3a9c1e-...] AccessLog - POST /transfers -> 204 (11 ms)
```

> [!WARNING]
> MDC is stored in a `ThreadLocal`. If a handler passes work to another thread (`CompletableFuture.supplyAsync`), the context does **not** move over automatically. Copy it by hand: `var ctx = MDC.getCopyOfContextMap();`, and in the task — `MDC.setContextMap(ctx)`.

In the report (the lab's `README.md`), show a log fragment of two parallel requests in which the lines are interleaved but can be separated by `requestId`.

## Stage 4: Testcontainers — Tests on a Real PostgreSQL (2 pts)

```java
@Testcontainers
class PostgresClientRepositoryIT {

    @Container
    static final PostgreSQLContainer<?> PG = new PostgreSQLContainer<>("postgres:16-alpine");

    private ClientRepository repo;

    @BeforeEach
    void setUp() throws SQLException {
        var cfg = new AppConfig(PG.getJdbcUrl(), PG.getUsername(), PG.getPassword(), 0, 2);
        DataSource ds = Database.create(cfg);         // your method: Hikari + schema.sql
        try (var c = ds.getConnection(); var st = c.createStatement()) {
            st.execute("TRUNCATE clients RESTART IDENTITY");   // a clean state for every test
        }
        repo = new JdbcClientRepository(ds);
    }

    // the same scenarios as with H2 in lab 10: transfer, rollback, duplicate
}
```

* A `static` container → one for the whole test class (starting it takes seconds).
* Move the repository tests from lab 10 into a **shared abstract class** `AbstractClientRepositoryContract` with an abstract method `createDataSource()` and two subclasses: `H2...IT` and `Postgres...IT`. This way the same contract is checked on both databases.
* Add an **API test**: start the server on port `0` with the database from the container and use `HttpClient` to check the scenario "create two clients → deposit → transfer → check the balances → a transfer above the balance gives 422".
* Name integration tests `*IT` and run them with `maven-failsafe-plugin` (`mvn verify`), and unit tests with surefire (`mvn test`).

> [!NOTE]
> How does H2 differ from PostgreSQL? For example, in case-sensitive string comparison, `TIMESTAMP` types, `ON CONFLICT` and error codes (`SQLState`). A test that is "green on H2" does not guarantee that the code works on the production database.

## Stage 5: Docker and Docker Compose (2 pts)

### Dockerfile (Multi-Stage)

* the `build` stage: `maven:3.9-eclipse-temurin-21`; first `COPY pom.xml` + `mvn dependency:go-offline` (layer caching), then `COPY src` and `mvn package -DskipTests`;
* the run stage: `eclipse-temurin:21-jre-alpine`, only the fat JAR, a user that is **not** root, `EXPOSE 8080`, `ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]`;
* `.dockerignore`: `target/`, `.git/`, `.idea/`, `.env`.

### compose.yaml

* the `db` service: `postgres:16-alpine`, a volume for the data, a `healthcheck` with `pg_isready`;
* the `app` service: `build: .`, `ports: "8080:8080"`, environment variables from `.env` (`DB_URL=jdbc:postgresql://db:5432/bank`), `depends_on: db: condition: service_healthy`, its own `healthcheck` on `/health` (`wget -qO- localhost:8080/health`).

### Acceptance (Show It to the Instructor)

```bash
docker compose up -d --build
docker compose ps                         # both services (healthy)
curl -s localhost:8080/health             # {"status":"UP","db":"UP"}
# ... the scenario from stage 2 ...
docker compose restart app                # the data is still there
docker compose stop db
curl -i localhost:8080/health             # 503, the application did NOT crash
docker compose start db
curl -s localhost:8080/health             # UP again (the pool restored the connections)
docker compose down
```

> [!IMPORTANT]
> Inside the Compose network the database is reachable as `db:5432`, not `localhost:5432`. `localhost` in the `app` container is the container itself.

### No Points

* GitHub Actions: a workflow that runs `mvn verify` on every push (Testcontainers work on `ubuntu-latest` without any setup) and builds the image.
* Graceful shutdown: a `Runtime.getRuntime().addShutdownHook` that stops the `HttpServer` (`server.stop(5)`) and closes the pool. Check it with `docker compose stop app`: the logs must show a clean shutdown, not an abrupt stop.
